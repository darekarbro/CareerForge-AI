## Groq support

server/.env.example now contains GROQ_API_KEY, GROQ_MODEL=openai/gpt-oss-120b and GROQ_TIMEOUT_MS=30000. Copy those settings into server/.env, insert your key and restart the backend. openai/gpt-oss-20b is also supported.

Groq is the first provider for all six operations, followed by OpenRouter, Gemini and the offline fallback. Supported Groq defaults request strict JSON schemas; other configured Groq models use JSON-object mode plus local validation. All remote requests honor cancellation and bounded timeouts. Settings shows configured models and the selected provider. Five Groq tests cover six successful actions, fallback/error paths, placeholder keys, schema construction/model persistence and cancellation.

The optional Gemini default was updated to [gemini-3.8-flash](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-flash). Its ATS prompt receives a derived actual word count while retaining the existing capped structured-data payload. Gemini retains its capped structured-data payload; a regression verifies that additional raw resume text is not transmitted.

## Deployment and compatibility

- Use a private random production JWT secret, an available persistent MongoDB and explicit frontend origins. Configure trusted proxy settings for your actual deployment.
- Startup repairs legacy data described above before creating indexes. Existing document IDs and resume content are preserved during version renumbering. Back up a persistent database before deployment.
- The job API now returns 202 for expensive operations. External API clients must follow processing-job status/timeline and use job output after completion.
- Development MongoDB is temporary, and an in-process queue is not durable across restarts. Private local uploads need persistent storage in deployment.
- Offline scoring is explicitly heuristic. Model validity and live service credentials/quotas still require environment-specific acceptance testing.
